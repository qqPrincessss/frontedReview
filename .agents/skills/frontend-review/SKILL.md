# 前端代码专项评判

> 本 Skill 补充浏览器和前端框架场景，不新增评分维度。所有结论仍必须映射到 `srp`、`abstraction`、`naming`、`dry`、`coupling`、`readability` 或 `consistency`。

## 一、组件与职责

好信号：

- 展示、交互状态、服务调用和领域决策的边界清晰；
- 组件 API 小而明确，props 表达业务意图；
- 可复用逻辑在确有复用或复杂状态边界时提取；
- 父子组件的数据所有权明确，更新方向可追踪。

坏信号：

- 单个组件同时处理请求、缓存、权限、表单、路由和大量展示分支；
- 子组件直接修改父级或全局内部状态；
- 大量布尔 props 组合出互相冲突的模式；
- 为一个简单片段创建多层无行为包装。

通常映射：职责混杂到 `srp`，接口泄漏或状态所有权混乱到 `coupling`，无价值包装到 `abstraction`。

## 二、状态与派生数据

好信号：

- 每份状态有一个权威来源；
- 可计算值在使用处派生，不与源状态重复存储；
- 更新使用最新状态，异步回调不会捕获过期值；
- 空、加载、成功、失败状态可以区分。

坏信号：

- 同一数据同时存在 props、局部 state 和全局 store，且需要手工同步；
- effect 仅用于同步可直接计算的派生状态；
- 多个布尔值组成不可能或矛盾状态；
- 更新依赖旧闭包值，可能覆盖并发更新。

不要仅因为存在局部 state 就判定设计不佳；需要指出可见的重复来源、竞态或非法状态。

## 三、Effect 与资源生命周期

好信号：

- effect 只同步外部系统，依赖项与读取值一致；
- 事件监听、定时器、订阅、Observer 和对象 URL 有对应清理；
- 请求具有取消、过期结果忽略或序列控制；
- 开发模式重复执行不会产生不可逆副作用。

坏信号：

- render 期间执行请求、订阅或写外部状态；
- effect 缺少必要依赖并读取可能变化的值；
- 注册监听或定时器但没有清理；
- 较早请求可能覆盖较晚请求结果；
- 清理函数引用了错误实例，导致资源残留。

资源泄漏和竞态通常映射到 `coupling` 或 `readability`；只有当前 diff 能证明主要行为错误时才使用 `error`。

## 四、异步流程和错误处理

好信号：

- 用户触发的异步操作有加载、防重复和失败反馈；
- Promise 被等待、返回或明确处理；
- 失败不会遗留半完成 UI 或脏状态；
- 组件卸载或参数变化后，旧结果不会继续覆盖新状态。

坏信号：

- fire-and-forget Promise 可能产生未处理拒绝；
- `catch` 为空或只打印日志但 UI 永久停留在 loading；
- 没有 `finally` 或等价路径恢复临时状态；
- 多次点击可以重复提交不可幂等操作。

不要假设外部函数一定失败或一定幂等；必须根据当前签名、调用方式和状态变化说明条件。

## 五、列表、标识与渲染行为

好信号：

- 列表 key 来自稳定业务标识；
- 条件渲染不会错误地显示 `0`、空字符串或对象；
- 状态更新保持引用和变更语义可预测；
- 昂贵计算只在有证据表明确实昂贵且频繁时优化。

坏信号：

- 可重排列表使用数组索引 key，可能把状态绑定到错误条目；
- 原地修改 state 后复用原引用；
- render 中持续创建大规模重复计算并已有可见性能路径；
- 不稳定 key 导致输入框、焦点或组件状态重置。

不要把所有新对象、内联回调都视为性能问题。必须有规模、频率、memo 边界或可见行为证据。

## 六、可访问性与交互语义

好信号：

- 交互使用正确的原生元素；
- 表单控件有可访问名称和错误关联；
- 键盘、焦点和禁用状态与鼠标行为一致；
- 动态状态变化在必要时可被辅助技术感知。

坏信号：

- 用不可聚焦的 `div` 代替按钮且没有完整键盘行为；
- 图标按钮没有可访问名称；
- label 与输入框没有关联；
- 只依靠颜色表达错误或状态；
- 弹层打开后焦点丢失或无法关闭。

可访问性问题根据结构归入 `abstraction`、`readability` 或 `consistency`，不要创建不存在的 accessibility 维度。

## 七、类型和边界数据

好信号：

- API、路由参数、存储和用户输入在边界处验证；
- 联合类型表达真实状态，穷尽处理明确；
- null/undefined 和可选字段语义一致；
- 类型缩小基于运行时证据，而不是强制断言。

坏信号：

- 使用 `as`、非空断言或 `any` 绕过尚未验证的外部数据；
- 类型声明与运行时返回结构明显不一致；
- 可选字段在未检查时直接访问；
- 字符串状态缺少统一枚举或联合约束并已产生分支遗漏。

不要因为单独出现一次类型断言就报告问题；需要指出被掩盖的具体不安全边界。

## 八、安全与敏感信息

检查当前 diff 中可见的：

- 未经转义或净化的 HTML 注入；
- token、密钥、连接串或隐私数据进入前端包、日志或 URL；
- 用户输入直接进入导航、请求、存储或 DOM 危险入口；
- 权限判断只存在于 UI，而服务端操作仍可直接调用。

安全是影响类型，不是新增评分维度。依赖和信任边界问题通常映射到 `coupling`；隐藏控制流和不安全转换可映射到 `readability` 或 `abstraction`。

## 九、避免常见误报

- 不要求所有组件都使用 memo、useMemo 或 useCallback；
- 不把缺少分号、引号风格、导入顺序等格式问题列为 issue；
- 不在没有证据时声称某个 Hook、框架 API 或浏览器能力一定不兼容；
- 不因组件行数较多就自动判定违反 SRP；
- 不把服务端才能保证的授权责任错误地要求前端独立完成；
- 不假设未展示的父组件、CSS、测试或服务端实现。

评判重点是当前 diff 可证明的行为、边界和维护风险，而不是套用框架口号。
